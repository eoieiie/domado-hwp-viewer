# 도마도 HWP 뷰어

한컴오피스 없이 `.hwp` / `.hwpx` 를 읽는 macOS 앱.

## 왜 만들었나

학교에 낼 신청서가 hwp로 왔는데, 맥에서 열 방법이 없었다.
한컴오피스는 유료 구독이고, 온라인 변환 사이트는 학교 서류를 남의 서버에 올려야 한다.
결국 파일 안에 뭐가 들었는지 확인하려고 파서를 짜기 시작했고, 그게 이 앱이 됐다.

목표는 하나다. **한국에서 온 파일을 맥에서 여는 가장 빠른 방법.**
기능 개수로 승부하지 않는다. 뭘 넣기 전에 이 문장을 강화하는지부터 본다.

- 외부 의존성 0개. 표준 라이브러리와 시스템 프레임워크만
- 실행 파일 1.1MB
- 네트워크 통신 없음. 파일이 이 맥 밖으로 나가지 않는다

## 기능

- hwp / hwpx 읽기. 확장자가 틀려도 컨테이너 시그니처로 판별한다
- 표를 격자로 복원. 행·열 주소와 가로·세로 병합까지
- 문서 내 검색, 이미지 추출
- 본문 텍스트 치환. 서식·표·이미지를 안 건드리고 새 파일로 저장
- zip 풀기·만들기. 한글 파일명이 깨지지 않는다
- 우클릭 → 서비스 → 윈도우 전송용으로 압축

## 쓰기

```bash
swift build -c release --product HwpViewer   # 앱
bash Tools/build-app.sh                      # 앱 번들로 설치
```

터미널에서:

```bash
hwpcli 문서.hwp                 # 본문
hwpcli 문서.hwp -t              # 표 구조
hwpcli 문서.hwp -r              # 문단 구조 점검
hwpcli 문서.hwp -e "옛말=>새말"  # 치환 → 문서_수정.hwp
hwpcli 압축.zip -z              # zip 목록, 이름 상태 판정
hwpcli 압축.zip -x 폴더          # 풀기
hwpcli -c 새.zip 파일들          # 묶기
```

## 만들면서 알게 된 것

### hwp는 3겹이다

```
OLE 복합 파일(CFBF)          ← 파일 안에 FAT·디렉터리가 있는 작은 파일시스템
└─ BodyText/Section0
   └─ raw DEFLATE
      └─ 레코드 스트림       ← [32비트 헤더][페이로드]
```

헤더가 `tag(10) | level(10) | size(12)` 로 눌려 있고, `size == 0xFFF` 면 다음 4바이트가
진짜 크기다. 본문은 `tag 67`, UTF-16LE.

**제어문자 1~8, 11~23은 16바이트를 차지한다.** 2바이트로 세면 그 뒤 모든 글자가 밀린다.
여기서 한참 헤맸다.

### 표는 빈 자리까지 그려야 맞는다

세로로 병합된 셀은 아래 행에 등장하지 않는다. 각 행에서 시작하는 셀만 그리면
그 뒤가 전부 한 칸씩 왼쪽으로 밀린다. 왼쪽에 병합된 머리 열을 두는 한국 서식은
거의 다 이렇게 어긋나 있었는데, 화면만 봐서는 "원래 저런 표인가" 싶어서 한참 못 알아챘다.

### 파일을 고치는 건 안 고치는 것보다 어렵다

hwp를 고치다 실패하면 **경고 없이 안 열리는 파일**이 남는다. 그래서 이 기능은
뭘 하느냐보다 **뭘 거부하느냐**로 설계했다.

- 컨테이너를 재구성하지 않는다. 본문 섹터에 덮어쓰고 길이만 고치고 나머지는 원본 그대로
  복사한다. 자리가 모자라면 파일 끝에 붙이되, 할당표가 이미 비었다고 표시한 자리만 쓴다
- `PARA_HEADER` 필드 오프셋은 스펙이 아니라 실제 문서를 읽어 알아낸 거라, `-r`이 매번
  재검증한다. 머리 레코드가 신고한 개수를 뒤따르는 레코드에서 다시 세어 대조한다
- 제어문자를 가로지르거나 서식이 중간에 바뀌는 구간은 건너뛴다
- 만든 파일을 다시 읽어 확인한 뒤에야 넘긴다. 본문 밖 스트림이 전부 바이트 동일한지까지

**이 검사가 실제로 큰 버그를 잡았다.** 문단의 본문·서식 레코드는 머리와 같은 레벨이
아니라 한 단계 아래에 있다. 같은 레벨로 묶었더니 모든 문단이 "본문 0자"로 나왔고,
그대로 갔으면 모든 글자 위치를 엉뚱한 레코드에 썼을 것이다.

### 한글 파일명은 양쪽으로 깨진다

**윈도우 → 맥.** 알집과 탐색기는 파일명을 CP949로 쓰고 "UTF-8이다"라고 알리는 비트를
켜지 않는다. macOS는 비트가 없으면 CP437로 읽어서 `과제제출.hwp` 가 `????????.hwp` 가 된다.

**맥 → 윈도우.** 이쪽이 덜 알려져 있다. macOS는 파일명을 자모가 분리된 채로 들고 있고,
맥 기본 압축은 그걸 그대로 넣으면서 UTF-8 표시도 안 한다. 자모가 분리된
`보고서 최종본.hwp` 를 넣고 재봤다.

| | UTF-8 표시 | 이름 |
|---|---|---|
| 맥 기본 압축 | 없음 | 47바이트, 자모 분리된 채로 |
| 도마도 | 있음 | 30바이트, 합쳐서 |

**두 가지가 동시에 틀린다.** 그리고 만든 맥에서는 끝까지 멀쩡해 보인다.
그래서 압축을 열면 어느 쪽에서 깨지는지 판정해서 보여준다.

푸는 쪽은 `FileManager` 가 아니라 POSIX로 쓴다. `URL` 과 `FileManager` 는 경로를
`fileSystemRepresentation` 으로 통과시키면서 다시 분해해버린다. 이름을 복구해놓고도
디스크에는 분리된 채로 적혔다.

## 검증

스펙 문서 없이 만든 파서라 혼자 맞다고 우길 수가 없었다.

- 파이썬으로 참조 구현을 따로 짜서 Swift 출력과 diff. 120문단 완전 일치
- 편집 결과는 `olefile`(별개 CFBF 구현)로 재확인. 우리 리더로 우리 라이터를 확인하면
  순환 논증이다
- 압축은 파이썬 `zipfile` 로 CRC·플래그·정규형 확인
- **마지막은 한컴 한글로 직접 열어봤다.** 구조가 맞다는 것과 한글이 받아들인다는 건
  다른 문제다

한글 확인은 위험 경로별로 4건을 만들어 돌렸다.

| 경로 | 결과 |
|---|---|
| 글자 늘림 → 섹터 신규 할당 (172,544 → 173,056바이트) | 정상 |
| 글자 줄임 | 정상 |
| 큰 문서 + 그림 12장 (4.2MB) | 정상 |
| 한 문단에서 서식이 여러 번 바뀜 | 정상 |

가장 걱정했던 `PARA_LINE_SEG`(줄 높이를 옛 값 그대로 둔 것)와 섹터 확장이 둘 다
통과했다. 한글이 줄 정보를 다시 계산한다는 뜻이다.

## 안 되는 것

정직하게 적어둔다.

- **자동화된 테스트가 없다.** 회귀 확인은 이전 커밋으로 워크트리를 만들어 출력을
  diff하는 수동 방식이다. 제일 큰 구멍이고 다음에 할 일이다
- `.hwpx` 수정 미지원. 읽기는 된다. zip 쓰기는 됐는데 테스트할 hwpx 파일을 못 구했다
- `.alz` / `.egg` 미지원
- Spotlight 색인·Quick Look은 코드가 있는데 Developer ID 서명이 없어서 안 산다
- 화면에서 셀을 직접 클릭해 고치는 건 보류. 입력칸이 표 안에서 입력을 못 받는다
- 수정 후 `PrvText` 가 옛 텍스트로 남아 Finder 미리보기가 잠깐 어긋난다

## 구조

```
Sources/
├── HwpKit/          파서·편집기·압축. UI를 전혀 모른다
├── hwpcli/          터미널 도구. 검증은 항상 여기서 먼저 한다
├── HwpViewer/       SwiftUI 앱
└── HwpSpotlight/    Spotlight 임포터 (서명 대기)
```

`HwpKit` 이 UI 비의존이라 CLI·앱·Spotlight 셋이 같은 코어를 쓴다.
덕분에 뭐가 틀렸을 때 파서 문제인지 화면 문제인지 바로 갈린다.
표 버그를 잡은 것도 CLI 출력과 화면이 달라서였다.
